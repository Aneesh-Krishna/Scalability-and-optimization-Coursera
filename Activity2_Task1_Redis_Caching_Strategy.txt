TASK 1: IDENTIFY WHAT TO CACHE IN REDIS - HIGH-TRAFFIC E-COMMERCE PLATFORM
==========================================================================

Scenario: An e-commerce platform serving millions of users has slow product
pages, high server load from frequent database queries, and a slow checkout.
The strategy below places a shared Redis cluster between all application
servers and the database, so every server reads and writes the same cache.

SYNCHRONIZATION ACROSS SERVERS
------------------------------

1. One shared cache: All application servers connect to the same Redis
   Cluster instead of keeping separate in-memory caches. Every server sees
   the same sessions, carts, and product data, so a user can be routed to
   any server.

2. Cache-aside for read-heavy data (products, categories, reviews, search):
   The app checks Redis first. On a miss, it reads the database, stores the
   result in Redis with a TTL, and returns it.

3. Write-through for critical data (carts, prices, inventory): When the data
   changes, the app updates the database and Redis together, so the cache
   never serves outdated values.

4. Invalidation on change: When an admin edits a product or price, the app
   deletes the related Redis keys and publishes an event on a Redis Pub/Sub
   channel. All servers receive it and refresh their data.

5. Atomic operations and locks: Inventory uses atomic DECR/INCR so
   concurrent orders on different servers cannot oversell. A short Redis
   lock (SET key value NX EX 10) prevents many servers from rebuilding the
   same expired key at once (cache stampede).

6. High availability and scaling: Redis Cluster shards data across several
   nodes to handle millions of users. Each primary node has a replica, and
   Redis Sentinel/Cluster failover promotes a replica if a node fails.
   Sessions and carts use persistence (AOF) so they survive a restart.


WHY THESE EXPIRATION TIMES?
---------------------------

- Sessions (24h sliding) and carts (7 days) are tied to user activity, so
  active users are never logged out or lose their cart, while abandoned
  data expires on its own and frees memory.
- Product details and categories change rarely, so longer TTLs (30 min-1h)
  combined with invalidation on change give high hit rates and fresh data.
- Prices and inventory affect money and orders, so they have the shortest
  TTLs, are written through on every change, and are confirmed in the
  database at checkout.
- Search results and deals (10 min) repeat often but must reflect new
  products and deal start/end times.
- Checkout data (30 min) only needs to last as long as one checkout.


DATA THAT SHOULD NOT BE CACHED
------------------------------

- Payment card details: never stored in Redis (security and PCI compliance).
- Final order records and payment confirmation: always written to and read
  from the database as the source of truth.
